# ユーザー詳細 要件定義書

| 項目 | 値 |
| --- | --- |
| 対象画面 | 新設（現行 `/admin/user_edit?id=` は表示不良） |
| 画面 ID | SCR-A-003 |
| 正本区分 | 本書を正本とする |
| owner | product |
| last_reviewed | 2026-07-31 |

## 1. 文書目的

- 本書は、ユーザー詳細の要件を定義する。本画面は独立した画面として新設する。
- 全画面に共通する権限、UI 規則、監査ログ、通知、用語は共通編を参照する。本書は本画面に固有の要件を扱う。
- 利用者の横断検索と一覧は本書の対象外とし、`11_admin_user_management.md` で扱う。

## 2. 画面概要

- 利用者 1 名に関する確認と対応を 1 画面で完結させる画面。
- 利用者本人の画面では実行できない操作を運営側が行う。対象は §3.2 に挙げる範囲とする。
- 紐づくアンケートと請求の状況をまとめて確認し、それぞれの画面へ移動できる。
- ユーザー管理（SCR-A-002）が確認と横断操作を担うのに対し、本画面が個別編集の主戦場となる。

## 3. 想定利用者と対象範囲

### 3.1 想定利用者

- 運営全体を管理する Lv3・Lv4。顧客からの問い合わせに対して、状態確認と代行操作を行う。

### 3.2 対象範囲

- 利用者 1 名の詳細情報の表示
- アカウント情報の変更
- パスワードの変更・再発行（管理者代行）
- 紐づくアンケートと請求状況のまとめ確認
- 招待中アカウントに対する招待の再送

### 3.3 対象外

- 利用者の横断検索・一覧・アカウントの停止（`11_admin_user_management.md`）
- アンケートの内容と状態の操作（`13_admin_survey_management.md`、`14_admin_survey_detail.md`）
- 請求金額と入金状態の操作（`15_admin_billing.md`）
- 利用者本人によるパスワード変更（利用者向け画面で扱う）

## 4. 画面要件

### 4.1 共通構成

- ヘッダー、サイドバー、パンくず、フッターを表示する（`01_admin_common_ui.md` §2）。
- 画面タイトルに対象の利用者を識別できる情報（ユーザー ID、氏名）を表示する。
- 画面は上から、アカウント情報、パスワード操作、紐づくアンケート、請求状況、操作ログの順に配置する。
- ユーザー管理（SCR-A-002）へ戻る導線を配置する。

### 4.2 アカウント情報

次を表示し、運営側で変更できる。

| 項目 | 表示 | 変更 |
| --- | --- | --- |
| ユーザー ID | 可 | 不可 |
| 会社名 | 可 | 可 |
| 氏名 | 可 | 可 |
| メールアドレス | 可 | 可 |
| 電話番号 | 可 | 可 |
| プレミアムの契約状態 | 可 | 可 |
| アカウント状態 | 可 | 不可（ユーザー管理で操作する） |
| 登録日時 | 可 | 不可 |
| 最終ログイン日時 | 可 | 不可 |

- 変更は入力後の保存操作で確定する。保存前に画面を離れる場合は確認ダイアログを表示する（`01_admin_common_ui.md` §8）。
- メールアドレスを変更した場合の本人への通知の要否は §11 で確定する。
- 変更内容は監査ログの記録対象（代行変更）とする（`02_admin_common_audit_log.md` §3）。

表示・変更する項目の最終確定は §11 で扱う。

### 4.3 パスワードの変更・再発行

利用者本人の画面では実行できない操作として、運営側が次を行う。

| 系統 | 動作 |
| --- | --- |
| パスワード初期化メールの送信 | 対象本人へ初期化メールを送信し、本人が新しいパスワードを設定する |
| 管理者による直接設定 | 管理者が新しいパスワードを直接設定する。理由の入力を必須とし、実行後に対象本人へ通知メールを送信する |

- 管理者による直接設定は Lv4 のみが実行できる（`00_admin_common_permissions.md` §4）。Lv4 以外には操作要素を表示しない。
- 直接設定は確認ダイアログ内で理由を入力する（`01_admin_common_ui.md` §7.2）。入力した理由は監査ログに記録する。
- 設定したパスワードの値は画面に表示せず、メール本文にも記載しない。

### 4.4 紐づくアンケート

- 対象の利用者が作成したアンケートを一覧で表示する。
- 各アンケートについて、アンケート ID、タイトル、会期、状態、名刺データ化の申込有無を表示する。
- 一覧から対象のアンケート詳細（SCR-A-005）へ遷移する。
- 表示件数が多い場合はページングに対応する（`01_admin_common_ui.md` §4.3）。

### 4.5 請求状況

- 対象の利用者に紐づく請求を一覧で表示する。
- 各請求について、請求月、請求金額、入金確認日を表示する。入金確認日が未記録の請求は入金未確認として扱う（`15_admin_billing.md` §4.7）。
- 一覧から請求管理（SCR-A-006）へ遷移する。

### 4.6 招待の再送

- アカウント状態が「招待中」の場合、招待メールの再送とキャンセルの操作を表示する。
- 再送時は新しいリンクを発行し、有効期限を再度 72 時間とする（`00_admin_common_permissions.md` §7.2）。

### 4.7 操作ログ

- 対象の利用者に対して行われた運営側の操作を、時系列で表示する。
- 表示するのは監査ログの記録対象のうち、当該利用者を対象とする操作とする（`02_admin_common_audit_log.md` §3）。
- 横断ログと本画面の個別ログは同一のデータを参照する。

### 4.8 追加要件（あったほうが良い）

| 要件 | 内容 |
| --- | --- |
| メールの本人到達確認 | 利用者招待メール（再送）、パスワード初期化メール、パスワード変更の本人通知（§5）が本人へ到達したかを画面上で確認する |

本要件は実現方式が未確定である。実現可否を開発側へ確認したうえで導入を判断する（§11）。

## 5. 通知

本画面の操作を起点として次の通知が発火する（`03_admin_common_notifications.md` §2）。

| 契機 | 通知 | 宛先 |
| --- | --- | --- |
| 招待を再送したとき | 利用者招待メール（再送） | 招待先のメールアドレス |
| パスワード初期化を実行したとき | パスワード初期化メール | 対象の利用者本人 |
| Lv4 がパスワードを直接設定したとき | パスワード変更の本人通知 | 対象の利用者本人 |

パスワード変更の本人通知は、送信の要否を管理者が選択する形にはしない。

## 6. 権限とデータ範囲

| 権限レベル | 扱い |
| --- | --- |
| Lv1 | 本画面へアクセスできない |
| Lv2 | 本画面へアクセスできない |
| Lv3 | 全範囲の利用者を表示・編集できる |
| Lv4 | 全範囲の利用者を表示・編集できる。パスワードの直接設定を実行できる |

- 本画面は顧客情報を扱うため、Lv2 以下はテナント分離により到達しない（`00_admin_common_permissions.md` §3）。
- 権限判定はサーバー側で行う（`00_admin_common_permissions.md` §9.1）。

## 7. 状態と挙動

### 7.1 初期表示

- ユーザー管理から遷移した対象の利用者の情報を表示する。
- 各入力欄には現在の値を表示する。

### 7.2 保存

- 保存操作で変更内容を確定する。保存中はボタンを非活性化し、二重実行を防ぐ（`01_admin_common_ui.md` §7.3）。
- 保存に成功した場合は画面上部に成功メッセージを表示し、表示内容を更新後の値へ更新する。
- 保存に失敗した場合は入力内容を保持し、失敗した旨を表示する。

### 7.3 本人編集との競合

- 利用者本人が同じ項目を編集している間に運営側が変更した場合、どちらの値を優先するかは §11 で確定する。
- 競合が検出できる場合は、保存時に競合が発生した旨を表示し、上書きの可否を確認する。

### 7.4 操作の記録

次の操作は監査ログに記録する（`02_admin_common_audit_log.md` §3）。

- アカウント情報の代行変更
- パスワード初期化メールの送信
- パスワードの管理者直接設定（理由を含む）
- 招待の再送・キャンセル

## 8. 現行画面からの引き継ぎ

現行の `/admin/user_edit?id=` は表示が崩れており、動作する機能を特定できない。本画面は新設として全機能を新たに実装する。

参考: 現行モック `03_admin/user-detail.html` は、基本情報、社内共有事項のメモ、権限区分（運用管理者／一般ユーザー／閲覧のみ）、機能ごとの利用可否、所有アンケートの一覧で構成される。権限区分と機能単位の利用可否は現行サービスの利用者側の権限体系と一致しない。モックは仕様上の正解とは扱わない。

## 10. 画面確認観点

モックアップ上で次を確認する。

- [ ] ユーザー管理から対象を選択して本画面へ遷移できる
- [ ] 画面タイトルに対象のユーザー ID と氏名が表示される
- [ ] アカウント情報が表示され、会社名・氏名・メールアドレス・電話番号・プレミアムの契約状態を変更して保存できる
- [ ] 変更不可の項目（ユーザー ID・アカウント状態・登録日時・最終ログイン日時）が入力できない状態で表示される
- [ ] 保存中はボタンが非活性化され、二重実行が発生しない
- [ ] 保存せずに画面を離れようとした場合に確認ダイアログが表示される
- [ ] Lv3 でログインした場合、パスワード直接設定の操作要素が表示されない
- [ ] Lv4 でパスワードを直接設定する際、確認ダイアログ内で理由入力が必須になる
- [ ] 設定したパスワードの値が画面に表示されない
- [ ] 紐づくアンケートの一覧が表示され、アンケート詳細へ遷移できる
- [ ] 請求状況が表示され、請求管理へ遷移できる
- [ ] アカウント状態が「招待中」の場合に招待の再送とキャンセルの操作が表示される
- [ ] 操作ログに、当該利用者に対する代行変更・パスワード操作が表示される
- [ ] Lv2 以下でログインした場合、本画面の URL へ直接アクセスしても表示されない

## 11. 画面外の確認事項

| # | 項目 | 内容 |
| --- | --- | --- |
| 1 | 本人編集との競合時の優先 | 利用者本人の編集と運営側の代行変更が競合した場合に、どちらを優先するかを確定する。後勝ちとするか、競合検出時に警告して選択させるかを決める。 |
| 2 | メールの本人到達確認 | §4.8 の実現可否を開発側へ確認する。現時点で「正しく実装できない」との報告があり、代替手段（送信ログの表示など）で足りるかを判断する。 |
| 3 | 表示・変更項目の確定 | §4.2 の項目一覧を確定する。利用者側の登録項目と突き合わせ、運営側が変更してよい項目の範囲を決める。 |
| 4 | メールアドレス変更時の通知 | メールアドレスを代行変更した際に、変更前・変更後のいずれかへ通知を送るかを確定する。 |
| 5 | 会社情報の変更範囲 | 会社名の変更が、同じ会社に所属する他の利用者へ波及するかを確定する。会社を独立したデータとして持つかを含めて決める。 |
| 6 | 請求状況の表示範囲 | 表示する請求を全期間とするか、直近の一定期間に限るかを確定する。 |
| 7 | 代行変更の対象外項目 | 運営側が変更してはならない項目があるかを確定する。パスワード以外に本人のみが変更できる項目があるかを確認する。 |
| 8 | 既定言語の保持先 | 名刺入力時の既定言語の保持先が本画面となる場合、§4.2 へ言語の項目を追加する必要がある。既定言語を利用者・アンケート・オペレーターのいずれに持たせるかは `19_admin_data_input_list.md` §11 の #6 と併せて確定する。 |
