# ユーザー詳細 要件定義書

| 項目 | 値 |

## 1. 文書目的

- 本書は、ユーザー詳細の要件を定義する。本画面は独立した画面として新設する。
- 全画面に共通する権限、UI 規則、監査ログ、通知、用語は共通編を参照する。本書は本画面に固有の要件を扱う。
- 利用者の横断検索と一覧は本書の対象外とし、`11_admin_user_management.md` で扱う。

## 2. 画面概要

- 利用者 1 名に関する確認と対応を 1 画面で完結させる画面。
- 利用者本人の画面では実行できない操作を運営側が行う。対象は §3.2 に挙げる範囲とする。
- 紐づくアンケートと請求の状況をまとめて確認し、それぞれの画面へ移動できる。
- ユーザー管理（SCR-A-002）が確認と横断操作を担うのに対し、本画面が個別編集の主戦場となる。

## 3. 想定利用者と対象範囲

### 3.1 想定利用者

- 運営全体を管理する Lv3・Lv4。顧客からの問い合わせに対して、状態確認と代行操作を行う。

### 3.2 対象範囲

- 利用者 1 名の詳細情報の表示
- アカウント情報の変更
- パスワードの変更・再発行（管理者代行）
- 紐づくアンケートと請求状況のまとめ確認
- 招待中アカウントに対する招待の再送

### 3.3 対象外

- 利用者の横断検索・一覧・アカウントの停止（`11_admin_user_management.md`）
- アンケートの内容と状態の操作（`13_admin_survey_management.md`、`14_admin_survey_detail.md`）
- 請求金額の確認（`15_admin_billing.md`）
- 利用者本人によるパスワード変更（利用者向け画面で扱う）

## 4. 画面要件

### 4.1 共通構成

- ヘッダー、サイドバー、パンくずを表示する（`01_admin_common_ui.md` §2）。
- 画面タイトルに対象の利用者を識別できる情報（ユーザー ID、氏名）を表示する。
- 画面本体を 2 カラムに分け、次の順に配置する（2026-08-17 改訂）。

| カラム | ブロック |
| --- | --- |
| 左 | アカウント情報（契約を含む）、所属グループ、監査ログ |
| 右 | 紐づくアンケート、請求状況、パスワード操作（メール送信履歴を含む）、対応履歴 |

- パスワード操作は日常的に使う操作ではないため、右カラムの先頭には置かない。
- 対応履歴は監査ログと同じ「この利用者に何があったか」の記録であり、記録系のブロックとまとめて後段に置く。
- 画面本体は 2 カラムで構成する。幅が足りない場合は右カラムを下へ送り 1 カラムにする（`05_admin_nonfunctional.md` §6.2）。カード内の表が切れないことを優先する。
- ユーザー管理（SCR-A-002）へ戻る導線を配置する。

### 4.2 アカウント情報

次を表示し、運営側で変更できる。

| 項目 | 表示 | 変更 |
| --- | --- | --- |
| ユーザー ID | 可 | 不可 |
| 会社名 | 可 | 可 |
| 氏名 | 可 | 可 |
| メールアドレス | 可 | 可 |
| 電話番号 | 可 | 可 |
| プレミアムの契約状態 | 可 | 可 |
| アカウント状態 | 可 | 不可（ユーザー管理で操作する） |
| 登録日時 | 可 | 不可 |
| 最終ログイン日時 | 可 | 不可 |

- 変更は入力後の保存操作で確定する。保存前に画面を離れる場合は確認ダイアログを表示する（`01_admin_common_ui.md` §8）。
- メールアドレスを変更した場合の本人への通知の要否は §11 で確定する。
- 変更内容は監査ログの記録対象（代行変更）とする（`02_admin_common_audit_log.md` §3）。

表示・変更する項目の最終確定は §11 で扱う。

### 4.3 パスワードの変更・再発行

利用者本人の画面では実行できない操作として、運営側が次を行う。

| 系統 | 動作 |
| --- | --- |
| パスワード初期化メールの送信 | 対象本人へ初期化メールを送信し、本人が新しいパスワードを設定する |
| 管理者による直接設定 | 管理者が新しいパスワードを直接設定する。理由の入力を必須とし、実行後に対象本人へ通知メールを送信する |

- 管理者による直接設定は Lv4 のみが実行できる（`00_admin_common_permissions.md` §4）。Lv4 以外には操作要素を表示しない。
- 直接設定は確認ダイアログ内で理由を入力する（`01_admin_common_ui.md` §7.2）。入力した理由は監査ログに記録する。
- 設定したパスワードの値は画面に表示せず、メール本文にも記載しない。

### 4.4 所属グループ

- 対象の利用者が参加しているグループを一覧で表示する。グループはアンケートを複数名で共同編集する単位であり（`user/05_group_edit_requirements.md` §2）、名刺データ化の作業グループ①〜⑧とは別の概念である（`04_admin_common_glossary.md` §2）。
- 各グループについて、グループ名、対象の利用者の権限（管理者 / 一般）、対象の利用者の状態（加入済 / 招待中 / アドレスエラー）、メンバー数、請求先の設定（作成者情報 / グループ専用）を表示する。権限・状態の値は `user/05_group_edit_requirements.md` §3.4 に従う。
- 1 人の利用者が複数のグループに参加している場合はすべて表示する。参加しているグループが無い場合はその旨を表示する。
- 本画面では参照のみとする。グループの作成・メンバーの追加・権限の変更は利用者側のグループ編集画面で行う。管理者による代行操作の要否は §11 で確定する。
- 請求先の設定を併記するのは、グループ専用の請求先が設定されている場合に請求の宛先が利用者本人と異なるためである（`user/05_group_edit_requirements.md` §3.3）。§4.6 の請求状況と併せて確認する。

### 4.5 紐づくアンケート

- 対象の利用者が作成したアンケートを一覧で表示する。
- 各アンケートについて、アンケート ID、タイトル、会期、状態、名刺データ化の申込有無を表示する。
- 一覧から対象のアンケート詳細（SCR-A-005）へ遷移する。
- 表示件数が多い場合はページングに対応する（`01_admin_common_ui.md` §4.3）。
- 対象の利用者のアンケートをまとめて確認する導線を配置し、アンケート管理（SCR-A-004）を当該ユーザーで絞り込んだ状態で開く（`01_admin_common_ui.md` §4.1.1）。
- 表示するアンケート数は、対象の利用者に紐づくアンケートから算出する。

### 4.6 請求状況

- 対象の利用者に紐づく請求を一覧で表示する。
- 各請求について、請求月、対象アンケート、請求金額、支払期日を表示する。
- 一覧から請求管理（SCR-A-006）へ遷移する。遷移時は当該ユーザーで絞り込んだ状態で開く（`01_admin_common_ui.md` §4.1.1）。

### 4.7 招待の再送

- アカウント状態が「招待中」の場合、招待メールの再送とキャンセルの操作を表示する。
- 再送時は新しいリンクを発行し、有効期限を再度 72 時間とする（`00_admin_common_permissions.md` §7.2）。

### 4.8 対応履歴（2026-08-17 追加）

運営がこの利用者について残す申し送りを、1 件ずつの記録として持つ。「支払いが毎回遅れる」「電話は避けてメール希望」のような、次に対応する担当者へ引き継ぎたい事情を扱う。

| 項目 | 内容 |
| --- | --- |
| 対応日 | 対応した日付。記録日と異なる場合があるため入力できる |
| 担当 | 記録した運営アカウント。入力ではなく自動で入る |
| 内容 | 自由記述 |

- 記録は追記のみとする。1 つの自由記述欄へ書き足す形にすると、分量が増えたときに目で探すことになり、いつ誰が書いたかも追えない。
- 一覧は対応日の新しい順に並べる。既定では直近の数件だけを表示し、残りの件数を添える。すべて表示する操作を用意し、元へ戻せるようにする。既定の表示件数は※要確定（§11 の #12）。
- 記録が 1 件も無い利用者では、ブロックを 1 行へ畳み、記録を追加する導線だけを残す。件数の多い利用者と同じ高さを常に占有させないためである。
- 利用者には表示しない。運営内で共有する記録である旨を画面上に明記する。
- アカウント情報の変更（§4.2）と保存の単位を分ける。アカウント情報は利用者のデータを代行で書き換えるため変更理由の入力を必須とするが、対応履歴は運営自身の記録であり理由の入力までは求めない。
- 過去の記録を編集・削除できるようにするかは※要確定（§11 の #11）。

利用者側の「社内管理用メモ」（`user/06_bizcard_settings_requirements.md`）とは別物である。あちらは利用者が自社のために書くもので、本ブロックは運営が利用者について書くものとする。

### 4.9 監査ログ

- 対象の利用者に対して行われた運営側の操作を、時系列で表示する。
- 表示するのは監査ログの記録対象のうち、当該利用者を対象とする操作とする（`02_admin_common_audit_log.md` §3）。
- 横断ログと本画面の個別ログは同一のデータを参照する。

## 5. 通知

本画面の操作を起点として次の通知が発火する（`03_admin_common_notifications.md` §2）。

| 契機 | 通知 | 宛先 |
| --- | --- | --- |
| 招待を再送したとき | 利用者招待メール（再送） | 招待先のメールアドレス |
| パスワード初期化を実行したとき | パスワード初期化メール | 対象の利用者本人 |
| Lv4 がパスワードを直接設定したとき | パスワード変更の本人通知 | 対象の利用者本人 |

パスワード変更の本人通知は、送信の要否を管理者が選択する形にはしない。

## 6. 権限とデータ範囲

| 権限レベル | 扱い |
| --- | --- |
| Lv1 | 本画面へアクセスできない |
| Lv2 | 本画面へアクセスできない |
| Lv3 | 全範囲の利用者を表示・編集できる |
| Lv4 | 全範囲の利用者を表示・編集できる。パスワードの直接設定を実行できる |

- 本画面は顧客情報を扱うため、Lv2 以下はテナント分離により到達しない（`00_admin_common_permissions.md` §3）。
- 権限判定はサーバー側で行う（`00_admin_common_permissions.md` §9.1）。

## 7. 状態と挙動

### 7.1 初期表示

- ユーザー管理から遷移した対象の利用者の情報を表示する。ユーザー ID・会社名・氏名・メールアドレス・アカウント状態は、遷移元で選択した対象のものを表示する。
- 各入力欄には現在の値を表示する。

### 7.2 保存

- 保存操作で変更内容を確定する。保存中はボタンを非活性化し、二重実行を防ぐ（`01_admin_common_ui.md` §7.3）。
- 保存に成功した場合は画面上部に成功メッセージを表示し、表示内容を更新後の値へ更新する。
- 保存に失敗した場合は入力内容を保持し、失敗した旨を表示する。

### 7.3 本人編集との競合

- 利用者本人が同じ項目を編集している間に運営側が変更した場合、どちらの値を優先するかは §11 で確定する。
- 競合が検出できる場合は、保存時に競合が発生した旨を表示し、上書きの可否を確認する。

### 7.4 操作の記録

次の操作は監査ログに記録する（`02_admin_common_audit_log.md` §3）。

- アカウント情報の代行変更
- パスワード初期化メールの送信
- パスワードの管理者直接設定（理由を含む）
- 招待の再送・キャンセル

## 8. 現行画面からの引き継ぎ

現行の `/admin/user_edit?id=` は表示が崩れており、動作する機能を特定できない。本画面は新設として全機能を新たに実装する。

参考: 現行モック `03_admin/user-detail.html` は、基本情報・契約状態・所属グループ・所有アンケート・請求状況・パスワード操作・対応履歴・個別ログで構成される（2026-08-17 時点）。モックは仕様上の正解とは扱わない。

## 11. 画面外の確認事項

| # | 項目 | 内容 |
| --- | --- | --- |
| 1 | 本人編集との競合時の優先 | 利用者本人の編集と運営側の代行変更が競合した場合に、どちらを優先するかを確定する。後勝ちとするか、競合検出時に警告して選択させるかを決める。 |
| 2 | 表示・変更項目の確定 | §4.2 の項目一覧を確定する。利用者側の登録項目と突き合わせ、運営側が変更してよい項目の範囲を決める。 |
| 3 | メールアドレス変更時の通知 | メールアドレスを代行変更した際に、変更前・変更後のいずれかへ通知を送るかを確定する。 |
| 4 | 会社情報の変更範囲 | 会社名の変更が、同じ会社に所属する他の利用者へ波及するかを確定する。会社を独立したデータとして持つかを含めて決める。 |
| 5 | 請求状況の表示範囲 | 表示する請求を全期間とするか、直近の一定期間に限るかを確定する。 |
| 6 | 代行変更の対象外項目 | 運営側が変更してはならない項目があるかを確定する。パスワード以外に本人のみが変更できる項目があるかを確認する。 |
| 7 | プレミアムの契約状態 | 運営側で変更できる契約状態の値と、変更時に請求へ与える影響（当月請求の扱い、日割りの有無）を確定する。 |
| 8 | 既定言語の保持先 | 名刺入力時の既定言語の保持先が本画面となる場合、§4.2 へ言語の項目を追加する必要がある。既定言語を利用者・アンケート・オペレーターのいずれに持たせるかは `19_admin_data_input_list.md` §11 の #6 と併せて確定する。 |
| 9 | グループ情報の取得範囲 | §4.4 で表示するグループ情報の取得元と鮮度を確定する。利用者側のグループ編集画面（`user/05_group_edit_requirements.md`）が正となるが、管理者画面から参照する際の反映遅延を許容するかを決める。 |
| 10 | グループの代行操作 | §4.4 を参照のみとするか、運営側でメンバーの追加・削除・権限変更を代行できるようにするかを確定する。代行を許す場合は監査ログの記録対象に加える。 |
| 11 | グループ単位の請求との関係 | グループ専用の請求先が設定されている場合、そのグループのアンケートの請求が §4.6 の請求状況に含まれるかを確定する。請求の宛先が利用者本人と異なるため、本画面の請求状況に出すか、グループ側でのみ扱うかを決める。`15_admin_billing.md` と併せて確認する。 |
| 12 | 対応履歴の記録の扱い | §4.8 の記録を、追記のみとするか編集・削除も許すかを確定する。誤記の訂正手段を持たない場合の運用を併せて決める。 |
| 13 | 対応履歴の既定表示件数と項目 | 既定で表示する件数（暫定 2 件）と、種別（電話・メールなど）を項目として持つかを確定する。種別を持つと一覧を追いやすくなるが、入力の手数が増える。 |
| 14 | 対応履歴と問い合わせ管理の関係 | 社外からの問い合わせを別の仕組み（起票フロー）で管理する場合に、本画面の対応履歴とどちらを正とするかを確定する。カスタマーサポートの役割を持つかが決まってから判断する。 |
