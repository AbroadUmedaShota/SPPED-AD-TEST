# 管理者画面 リライト版仕様書の読み方

本フォルダの文書は、SPEED AD 管理者画面リファクタリング版のモックアップを作成するための要件定義書です。本フォルダを管理者画面要件の正本とします。

## 正本区分

- 本フォルダの文書を管理者画面要件の正本とする。
- 要件の根拠はスプレッドシート「管理者画面_たたき台」の各画面行とする。たたき台の内容を本書へ移し替えた時点で、本書が参照先となる。
- 旧資料は 2026-07-31 付で失効し、`docs/アーカイブ/旧要件定義書_20250521/`（旧要件定義書 v1.3）および `docs/アーカイブ/画面設計仕様admin_20260515/`（旧管理者画面仕様）へ退避済み。非機能要件のみ本フォルダ `05_admin_nonfunctional.md` へ引き継ぐ。同ファイルはモックアップ工程の対象外であり、参考資料（`status: reference`）として扱う。
- `03_admin/` 配下の HTML は現行モックであり、仕様上の正解とは扱わない。本文で引用する場合は「参考: 現行モック」と明記する。
- `data/` 配下のデータは参考のモックデータであり、実運用 DB とは扱わない。

## 対象

管理者画面（運営側が利用する画面）の全体。利用者向け画面の要件は `docs/リライト版仕様書/user/` で扱う。

管理者画面は、現行画面のリファクタリングと一部画面の新設の両方を含む。現行画面が存在するものは現行の機能を最低線として引き継ぎ、現行画面が存在しないものは新規要件として定義する。

## 本書で定義する範囲

- 管理者画面の表示内容、操作、画面遷移
- 一覧の検索条件・絞り込み条件・並び替え・表示件数
- 入力チェック、保存、実行、完了時の動き
- 権限レベルとデータ範囲による表示・操作の制御
- 通知・メールの発火点
- 監査ログとして記録する操作
- モックアップ上で確認する主な条件

## 今回の範囲外

- サーバーサイド実装・API・DB 設計（本番化工程で扱う）
- サーバー内部の詳細設計
- DB 物理設計
- インフラ構成の詳細
- 社内だけで扱う運用手順
- 旧画面、サンプル画面、検証用画面
- 利用者向け画面の要件（`docs/リライト版仕様書/user/` で扱う）

## 書き方の方針

- 「現行画面」は本番環境で稼働中の管理者画面を指す。現行画面の機能はリファクタリング後も引き継ぐ最低線として扱う。
- 画面上で確認・操作できる内容を本文要件として扱う。
- 各画面別ファイルの §10 は「画面確認観点」とし、モックアップ上で検証する項目を列挙する。API、DB、保管期間、インフラなど画面から確定できない内容は「画面外の確認事項」として扱う。
- 未決事項は本文に混ぜず、各ファイル末尾の「画面外の確認事項」に 1 行ずつ分離する。未決であっても要件本文は書き切る。
- 呼称・ステータス値が未確定のものは「※要確定」と明記する。
- 画面表示は文字と数値を基本とする。集計値は数値カードまたは表として定義する。
- 根拠のない将来案は本文要件にしない。

任意要件は次の 2 分類で扱う。見出しを分けて記載する。

| 分類 | 由来 | 位置づけ |
| --- | --- | --- |
| 追加要件（あったほうが良い） | たたき台 E 列の【あったほうが良い】 | 導入を前提とする追加。必須要件が満たされたうえで加える |
| 検討中の要件 | たたき台 H 列（検討中の機能） | 採否が未定。導入判断は「画面外の確認事項」で扱う |

## front-matter

各ファイルの先頭に次の front-matter を置く。画面別ファイルには `screen_id` を追加する。

```yaml
---
owner: product
status: draft
last_reviewed: YYYY-MM-DD
screen_id: SCR-A-xxx
---
```

`status` は `draft` / `review` / `approved` / `reference` のいずれかとする。`reference` はモックアップ工程の対象外とする参考資料に用いる。

`screen_id` は未採番の画面を許容する。未採番の場合は `未採番（※要確定）` と記載し、冒頭表の「画面 ID」と表記を揃える。採番そのものは各ファイルの「画面外の確認事項」で扱う。
