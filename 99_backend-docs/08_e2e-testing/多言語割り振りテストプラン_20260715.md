# 多言語割り振り検証テストプラン（PRD-SCN-420L／420M）

- 作成日: 2026-07-15
- 対象環境: 本番（`https://speed-ad.com`）
- 対象シナリオ: PRD-SCN-420L（一致3マス）→ PRD-SCN-420M（不一致6マス）を同一環境で連続実行
- 位置づけ: 2026-07-15のシナリオ再編（scenario-data.js）に基づく実行計画。判定ルール・判定タイミングの前提は README_prod420_worklog_20260715.md の実測に依拠

## 0. 目的と検証仮説

### 目的（未観測点に絞る）

1. **本丸**: 英語・中国語（簡体字）と判定されたレコードが、当該言語を対応可能とするオペレーターの入力キューに実際に計上されるか（420で唯一検証できずに終わった点）
2. 判定ルール仮説の統制条件での確認（一致→その言語／日本語絡み不一致→日本語／日本語なし不一致→判定不能）
3. **判定不能レコードのフォールバック先の特定**（全員に出る／日本語チームに出る／誰にも出ない=滞留）。「誰にも出ない」なら納品漏れ直結の不具合として起票
4. 言語フィルタDL（個別言語選択時）で判定不能レコードが取りこぼされないか

### 確定済みの前提（再検証しない）

- 「名刺の入力言語」は入力作業前・送信時点で自動付与される（2026-07-15確認）
- 回答言語はユーザー側回答データCSV「アンケートの回答言語」列に記録される（同上）
- 対応可能言語による**除外**は機能する（日本語を外したアカウントに日本語判定の作業が来ない=2026-07-10確認）

## 1. ブロッカーと事前決定事項

### B-1【最重要】送信可能な多言語アンケートの用意（要許可）

420は会期終了でSubmit無効（2026-07-15実証）。選択肢:

| 案 | 内容 | 利点 | 懸念 |
|---|---|---|---|
| (a) 420の会期再設定 | admin編集で終了日を延長 | 準備が軽い | 既存29件＋データ化完了状態が観測ノイズになる。完了→データ化中への状態巻き戻しの挙動が未知 |
| **(b) 検証用アンケート新設（推奨）** | 多言語設定（ja/en/zh-Hans）・オンデマンドで新規作成 | ベースライン0件で件数観測が明瞭。台帳がクリーン | 作成・データ化依頼の手間と課金。多言語=プレミアムオプションの設定要 |

**既定値: (b) 新設**。作成時に対応言語へ繁体字（zh-TW/zh-Hant）が設定可能か画面で確認だけ行い、可能なら記録する（PRD-SCN-420Cの前提①の消化。設定はしない）。

### B-2 オペレーター対応可能言語の設定（テストアカウント4つのみ変更）

| アカウント | Lv | 設定 | 役割 |
|---|---|---|---|
| abroadcrew02 | Lv4 | 日本語のみ | 管理・観測（admin/surveys・matching_list）＋日本語キュー観測 |
| abroadcrew03 | Lv3 | 日本語のみ | 照合担当＋日本語キュー観測 |
| abroadcrew04 | Lv2 | **英語のみ** | 英語判定キューの観測（帰属切り分け） |
| abroadcrew05 | Lv1 | **簡体字のみ** | 簡体字判定キューの観測（帰属切り分け） |

- 「英語のみ」「簡体字のみ」を分離することで、英語判定・簡体字判定の帰属を独立に観測できる（2026-07-10は「簡・英セット」だったため切り分け不可だった）
- 設定内容と適用時刻を記録し、**検証中は変更しない**。検証終了後に元へ復元
- 変更対象はテストアカウント4つのみ（実在オペレーターの設定には触れない）

### B-3 実オペレーター交絡（グローバルキュー）

入力キューは全アンケート横断のグローバルキューのため、日本語判定のテストレコードは実在の日本語対応オペレーターにも見え、送信→観測の間に消化される可能性がある。

- 対策1: **送信のたびに即時（数分以内に）4アカウントの件数を観測**する（まとめ送り→まとめ観測をしない）
- 対策2: 実行時間帯は入力作業が動いていない時間帯を優先（ユーザー指定があれば従う）
- 参考: 420の未入力13件は7/10〜14の4日間消化されずに残った実績があり、リスクは限定的とみられる（保証はなし）

### B-4 本番副作用の承知事項

- 回答送信で完了メール等が実際に送信される。新設アンケートのデータ化依頼・DLで課金が発生し得る
- テスト名刺は実顧客PIIなしのダミーのみ。証跡に他社の実データが映り込まないようマスクする
- 実行後クリーンアップ（Lv4でテスト回答・名刺データの整理）と、オペレーター言語設定の復元を行う

## 3. 実行フェーズ

### Phase 0: 環境準備（人間承認ポイントあり）

1. 検証用アンケート新設（B-1・要許可）: 多言語 ja/en/zh-Hans・オンデマンド・設問は自由記述1問で足りる。公開して回答URLを記録。繁体字の設定可否を画面で確認・記録（設定はしない）
2. オペレーター4アカウントの対応可能言語を B-2 のとおり設定・記録（適用時刻含む）
3. ダミー名刺9枚生成・対応表確定
4. ベースライン記録: 4アカウントの data_input_list 全グループ件数／admin/surveys の実際の件数

### Phase 1: PRD-SCN-420L（一致3マス）

各マスで「送信→即観測」を1サイクルとして繰り返す:

1. マス送信（言語選択→本文入力→名刺添付→送信200確認）
2. **入力作業前に**回答データCSVをDL→「名刺の入力言語」を確認（送信時自動判定の再現）
3. 4アカウント全部の data_input_list 件数を確認・スクショ（期待割り振り先のみ+1）
4. 3マス完了後: 割振先アカウントでグループ1（メール）を消化→グループ前進後の見え方を全アカウントで再観測（振り直しが起きないか）

**中断判定**: マス2（en×en）が04に出ない場合、以降のマスを消化する前に観測結果を整理してユーザーに報告（割り振りロジック自体が判定と別基準の可能性が高く、420Mの期待値が変わるため）。

### Phase 2: PRD-SCN-420M（不一致6マス）

1. 日本語絡み4マス（#4〜7）を送信→各送信後にCSV判定値と4アカウント件数を観測
2. 日本語なし2マス（#8〜9）を送信→判定不能の確認→**どのアカウントに出るかを4アカウント総当たりで特定**
3. 判定不能が誰にも出ない場合: 時間を置いて再観測（15分・60分）→それでも出なければ「滞留=納品漏れ」として起票対象に確定
4. 言語フィルタDL確認: 回答データCSVを「日本語のみ」「英語のみ」「中国語（簡体字）のみ」「すべての言語」の4パターンでDLし、各レコード（特に判定不能）の出力有無を記録

### Phase 3: 整理・復元

1. 9マスマトリクスに判定値・割り振り先を確定記入→「仕様確認（正本Wiki 25/63への追記提案）」「不具合（起票）」に分類
2. worklog（README_prod420L_worklog_20260715+.md）作成、scenario-data.js の stg_observation_status 更新
3. クリーンアップ: テスト回答・名刺データの整理（Lv4）、オペレーター言語設定の復元、DLファイル削除

## 4. ガードレール

- **実画面操作のみ**（Playwright実クリック・実入力。JSでのDOM直接操作は不可）
- **判定値の人間確認必須**（BUG-003: AI観測のみで断定しない。CSVの判定値はユーザーが目視確認するチェックポイントを設ける）
- 回答本文は必ず選択言語で記述（2026-07-10の交絡の再発防止）
- 対応可能言語設定は検証中固定。グループ消化中の設定変更をしない
- 認証情報を成果物・証跡・公開ファイルに書かない
- 送信→観測サイクルを崩さない（まとめ送りをしない=B-3対策＋どの送信でどの件数が動いたかの1:1対応を保つ）
