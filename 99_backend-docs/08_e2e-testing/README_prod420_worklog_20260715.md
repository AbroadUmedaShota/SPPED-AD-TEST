## 1. 結論

### ① 回答言語はユーザー側「回答データ」CSVに記録されている（機能実装済み）

- ユーザー側ダッシュボード → 420行のダウンロード → 「回答データ」で `0042000420.csv` を実DL成功
- 列構成: ID／名刺画像ファイル名（表）／名刺画像ファイル名（裏）／回答日時／テスト回答／**アンケートの回答言語**／**名刺の入力言語**／Q.01_テスト
- 「アンケートの回答言語」は全行に 日本語/英語/中国語（簡体字）が記録済み。7/10の🟡「完成データCSVに回答言語列がない」は「回答言語はユーザー側回答データCSV側に付く設計」と確定

### ② 「名刺の入力言語」は入力作業前・送信時点で自動付与される

- 照合一覧（全ステータス検索）: 420 = **総件数29・一致16・未入力13**
- 未入力13レコード（2026-07-10 16:30〜17:25送信・誰も入力作業をしていない）**全件に判定値が付与済み**（日本語4/英語2/中国語2/判定不能5）
- → 判定は人間の入力作業と無関係。「入力言語」という列名だが実体は送信時の自動判定

### ③ 判定ルール仮説が全29レコードと整合

| 回答言語×名刺言語 | 判定結果（実測） |
|---|---|
| 一致（ja×ja／en×en／zh×zh） | その言語 |
| 不一致・日本語が絡む（en×ja名刺、ja×en名刺、zh×ja名刺 等） | 日本語 |
| 不一致・日本語なし（zh×en名刺 等） | 判定不能 |

※正本Wiki（25/61/63）未記載の仮説。統制条件での確認は PRD-SCN-420M。

### ④ 7/10の「多言語ルーティング不発」結論は見直しが必要

- 7/10に「全レコードが日本語判定＝判定が機能していない」と結論したが、当時の全レコード（card11〜15含む）は**上記ルールなら日本語判定になる組合せ**だった（例: card14=ja回答×英語名刺→日本語）
- つまり「02/03にのみ割り振られ04/05に来ない」は判定ルールどおりの動作だった可能性が高い。**起票根拠は「判定の故障」ではなく「英語・中国語判定レコードの割り振り先が未観測」に変更すべき**
- 英語判定2件・中国語判定2件はその検証材料だったが、04/05のキューで確認する前にデータ化完了→キューから消滅し、420では検証機会を喪失

## 2. 検出した要確認事項・気づき

### 🟡 名刺なし回答が回答データCSVに出力されない（要確認）

- 回答数30件に対し回答データCSVは29行・全行名刺あり。名刺なし回答1件が含まれない
- PRD-SCN-420N の期待「回答データCSVには名刺なし回答も記録される」と食い違い。仕様か不具合か要確認

### 🟡 未入力13件を残したまま「データ化完了」ステータスになっている

- 実運用なら名刺13枚ぶんが入力されないまま納品完了扱いになる事象に相当（納品漏れリスク）
- 完了判定の条件（納期日での強制完了か）は要確認。判定不能レコードの滞留と関係する可能性（→PRD-SCN-420M）

### 🟡 会期終了後も回答フォームが操作できるがSubmitのみ無効

- 設問入力・名刺アップロード（「名刺画像を保存しました」トースト表示）まで正常に通り、Submitボタンだけがdisabledのまま
- 終了メッセージが出ないため回答者に送信できない理由が伝わらない（UX起票候補）
- テスト運用上の教訓: **420系シナリオは会期中にしか実行できない**（各シナリオの前提に追記済み）

### ✅ DLモーダルに「言語フィルタ」を発見（未シナリオ化だった機能）

- ダウンロードオプションに「すべての言語／中国語（簡体字）／日本語／英語」チェックボックスと「選択した言語に一致する回答のみ出力します」の説明
- 判定不能レコードが個別言語フィルタで取りこぼされないかは未検証 → PRD-SCN-420M ステップ6で対象化
