## 3.10 🔴 TC-10 一時ファイルパスの信頼境界テスト → IDOR発見（2026-07-13 追記・最重要）

顧客症状「別の回答ID・別社員CDに同一/他人の名刺画像」の**修正後ビルドでも残る発生経路**を狙い、送信ペイロードの `bizcard_tmp_photo_1/2`（クライアントが指定する一時ファイルパス）の信頼境界をAPI層でテストした。

| # | テスト | 結果 | 判定 |
|---|---|---|---|
| H1 | 同一セッションで**同一tmpを2送信が参照** | 1件目200(answer_id発行)・**2件目500** | tmpは1回で消費（move的）。同一画像の複製は起きない（症状の同セッション版は塞がれている） |
| H2 | **別セッション(別端末相当)がフレッシュな他人のtmpを参照** | 🔴 **200・answer_id発行（2/2再現）** | **IDOR成立**。所有権チェックなし |
| H3 | パストラバーサル `../334/...` | 422（tmpパス不正） | 検証あり・ブロック |
| H3d | tmp/以外の最終画像キー4種を参照 | 4/4とも422 | tmp/形式に固定・任意キー参照不可 |
| — | 非存在tmp（形式は正）を参照 | 500(server_error) | 🟡 堅牢性: 422でなく未処理例外 |

### 🔴 発見: bizcard一時ファイル参照に所有者チェックがない（IDOR）
- **実証（DL照合）**: セッションAがアップロードした名刺 `STG353-T10-R2-001` が、**別セッションBが送信した回答17791に保存されていた**（`0021500353_17791_1.jpg` の内容＝Aの画像）。2回目も回答17794で同様に成立（2/2）
- **機序**: `POST /survey-answer` の `bizcard_tmp_photo_*` はクライアント任意の文字列で、サーバは「形式が `stg/bizcards/tmp/tmp_*` か」だけを検証し、**そのtmpを誰がアップロードしたか（セッション所有権）を検証していない**。他人の未消費tmpパスを知れば、その名刺画像を自分の回答に取り込める
- **前提と限界**: tmpパスはUUIDv4で総当たりは非現実的。ただし**パスは漏れうる**——本テスト中に観測した419エラー応答はサーバ内部パスを露出（§3.7）、会場ネットワーク・共有端末・プロキシログ経由での露出も想定。tmpは1回で消費されるため、**レースで先に送った側が画像を取得し、負けた側は500で送信失敗（画像なし/欠損の温床）**
- **顧客症状との関係（正直な評価）**: THK事象の確定原因は独立連番の命名衝突（Backlog SPDAD2026-186・修正済み）であり、本IDORがTHK事象の原因だと断定はできない。ただし「別回答に他人の名刺が混入」という**同型の症状を、修正後ビルドでも独立に生み得る未修正の設計欠陥**。上司の言う「他の原因候補」として事実ベースで提示できる
- **推奨対策**: (1) tmp参照を作成元セッションに束縛し、クロスセッション参照は403で拒否 (2) 消費済み/非存在tmpは422で返す（現状500） (3) 名刺画像はPIIのため優先度高

## 3.13 TC-12 タイムアウト後の同時再送信（展示会の電波復帰シナリオ・2026-07-13 追記）

「放置」と「同時送信」は別々に検証済みだったが、**「通信断で送信失敗 → 回線復帰で全員が一斉に再送信」**という掛け合わせが未実施だったため追加:

- 12台が名刺アップロード済み → **全台オフラインにして送信試行（タイムアウト＝失敗）** → オンライン復帰 → **全台バリアで一斉再送信（35ms以内）**
- オフライン試行のサーバ到達: **0件**（＝失敗した送信は二重登録の元にならない）
- 再送信: 12/12成功
- DL照合（12件）: 回答ID全件一意・ファイル名重複0・**多重登録0**・画像取り違え0
- 結論: **タイムアウトした利用者が一斉に再送信しても、命名衝突・上書き・二重登録は発生しない**。オフライン失敗はサーバに届かないため、再送信時に各自ユニークな回答IDで1件だけ登録される

## 3.14 🟠 TC-13 応答遅延タイムアウト×複数タブ×同時再送信（最悪条件・重要）

上司メモ「電波状況が悪くて〜」仮説の本命検証。**応答が返ってこない型のタイムアウト**（オフラインではなく、送信は届くが応答が遅い）を、複数タブ開き＋全台同時再送で再現:

- 8台、各台が**2タブ開いた状態**（CSRFトークン競合の悪条件）
- 遅延回線（応答5秒）でtab1から送信 → クライアントは2.5秒で諦める（時間経過タイムアウト）
- tab1リロード→再アップロード → **全台バリアで一斉再送信（34ms以内）**

| 観測 | 結果 |
|---|---|
| attempt1（諦めた送信）のサーバ到達 | **8/8**（応答は返らなかったが**サーバは受理してレコード作成**）|
| attempt2（再送信） | 8/8成功 |
| 総レコード数 | **16件（8台×2件）** |
| 回答ID重複／ファイル名重複／上書き／取り違え | **すべて0** |
| **二重登録（同じ端末が2件）** | **8/8で発生（100%）** |

### 結論（顧客説明・恒久対策に直結）
- **オフライン型タイムアウト（TC-12）との決定的な違い**: オフラインは送信がサーバに届かず二重登録0。一方**応答遅延型は送信が届いてレコード化されるため、ユーザーが再送信すると必ず2件になる**
- **「電波が悪い会場で送信し直した来場者」は、高い確率で同じ名刺が2件登録される**——これは稀なレースではなく、遅い回線＋再送で**再現性100%**。上司メモの別原因仮説を実証データで裏付ける
- ただし**上書き・消失・命名衝突・取り違えは一切発生しない**（各レコードが別々の回答ID・別ファイル名で共存）。THK事故の「上書き消失」とは別物で、はるかに軽い「重複」
- 複数タブの悪条件下でも命名衝突・上書きは0。多タブはattempt1を419で止めることもなく、二重登録の発生に上乗せ影響なし
- **恒久対策の示唆**: サーバ側の冪等化（同一セッション・同一内容の短時間再送を重複登録しない）で防げる。名刺重複の"見た目"を減らす実効的な改善候補

## 4. 照合方法の注記（重要・再実施者向け）

- **保存画像は登録時の元画像とバイト一致しない（SHA-256全295枚不一致）**。サーバ側で再エンコードされるため、上司プランの「画像ハッシュ値: 登録時の元画像と保存画像が一致」は**現行仕様では成立しない**チェック項目
- 代替として、画像中央のID描画領域のテンプレート照合（正規化MSE）で内容同定した。最良候補と次点の距離差が約100倍あり同定は確実
- 再エンコードは決定的（同一入力→同一出力バイト）。zip内の同一ハッシュ検出は「同じ元画像が複数回使われた」検出として引き続き有効（P5・P2の意図的同一画像2組のみを正しく検出）
- この再エンコード仕様は「元画像（原本バイト）が保存されない」ことを意味し、**元画像復旧の論点（原本保全策の検討）に直結する観察**

## 5. 検出した気づき・観察事項

### ⚠️ 通信中断＋再回答で2レコード化（TC-04-2）
- 低速回線エミュレーション下で送信→応答前にリロードした場合でも、**1回目のPOSTはサーバ側で完了しレコードが残る**。ユーザーが「送信できなかった」と再回答すると、**同一名刺画像の付いた2レコード**になる
- ファイル名は回答IDごとに別名になるため上書き・消失はしないが、納品データ上は「同じ名刺が2件」に見える。**「電波状況が悪い会場で送信し直した来場者」の行動で自然に発生しうる重複メカニズム**として説明可能
- クライアント側の連打防止（TC-04-1）はあるが、リロード・ブラウザ強制終了経由の再送信はサーバ側で冪等化されていない

### 🟡 名刺なし送信・裏面のみのレコードが作れる（TC-04-7）
- 撮影済み名刺の表面を「削除」した後、裏面側の「再撮影」で表面用の画像を添付し、そのまま送信できた（回答ID 17478: 表面参照なし・裏面に表面画像）
- 表裏の整合チェック（表面必須など）がクライアント・サーバともに無い。データ化工程での混乱要因になりうる

### 🟡 回答画面に `id="bizcard-upload-modal"` が3重複
- 同一IDのDOM要素が3つ存在（名刺アップロードコンポーネントの多重インスタンス化）。今回の重複事象との直接因果は確認されていないが、ID指定のDOM操作が別インスタンスを掴む类のバグの温床になりうる
